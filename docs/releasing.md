# Подготовка публичного релиза

## 1. Проверки исходников

Выполни команды и полный Linux-прогон из [CONTRIBUTING.md](../CONTRIBUTING.md), просмотри `git diff --check`, `git diff` и список новых файлов `git status --short`.

```bash
git ls-files
gitleaks git --redact --log-opts='--all' .
pre-commit run --all-files
```

Отдельно убедись, что в добавляемых файлах нет конфигураций, маршрутов организации, рабочих IP, пользовательских имён, токенов или ссылок доступа. Не включай личные данные в скриншоты и примеры логов.

## 2. Проверка на одноразовом VPS

Перед объявлением серверных инструкций проверенными выполни для каждой заявленной ОС:

- Установка выбранного сценария с чистого образа; запиши точные версии ОС, ядра, Xray и клиента.
- Новый SSH-вход и `sudo -v` перед отключением root; повторная проверка после перезагрузки.
- Валидация `xray run -test -config /usr/local/etc/xray/config.json`, реальное соединение клиента и проверка выходного IP, DNS и DIRECT-маршрутов.
- При установке дополнений: повторный запуск установщиков, добавление/удаление тестового клиента, ошибка рестарта с восстановлением конфигурации, работа Stats API и таймеров.
- Бот: отказ постороннему чату, `/link`, `/qr`, `/traffic`, `/restart` и подтверждение удаления. Сравни `/traffic` с реальной квотой и интерфейсом сервера.
- Создание и восстановление бэкапа на отдельном VPS. Проверяй права файлов и системного пользователя бота после восстановления.

Локальные тесты подменяют команды Xray и systemd. Их успех не заменяет этот прогон. Не указывай в release notes проверки, которые фактически не проводились.

## 3. Публикация

После проверки и коммита собирай архив **из Git**, а не из рабочей папки:

```bash
# HEAD должен содержать все проверенные изменения.
git archive --format=tar.gz --prefix=tunnel-kit/ -o ../tunnel-kit-source.tar.gz HEAD
tar tzf ../tunnel-kit-source.tar.gz
```

Архив включает только файлы выбранного коммита; личные игнорируемые файлы рядом с исходниками в него не попадают. При публикации самого Git-репозитория история тоже становится доступна — проверь также метаданные коммитов и доступные ветки/теги.

На GitHub включи private vulnerability reporting и, если доступно для репозитория, secret scanning / push protection. Настрой обязательный успешный CI перед слиянием. Эти настройки делаются владельцем репозитория и не включаются добавлением YAML-файла.

В release notes укажи выполненные проверки, точные версии, ограничения роутерного гайда и известные ограничения из [SECURITY.md](../SECURITY.md).
